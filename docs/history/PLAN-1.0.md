# GraphLite 1.0 路线图（对标成熟图数据库）

> 回答两个问题：
>
> 1. **成熟图数据库是怎么从 MVP 走到成熟的？我们差在哪？**
> 2. **要达到那个成熟度，具体做什么？**
>
> 结论：**功能一个不删（按你的要求），但把优先级排对，让 1.0.0-rc.3 就足够日常使用。**
>
> 全部工作**不破坏已有数据文件**。

---

## 第 0 节：先纠正三个必须知道的事实

### 事实一：24 位页号的上限是 64 GiB，不是 640GB

```
24 位 = 16,777,216 页 × 4 KB = 68,719,476,736 字节 = 64 GiB
```

（之前分析里的"640GB"错了 10 倍。）

### 事实二：存在一个静默数据损坏点

属性指针 = 「高 24 位页号 + 低 8 位槽位」。代码是：

```rust
debug_assert!(page_id <= 0x00FF_FFFF, "PageId exceeds 24-bit address space");
((page_id & 0x00FF_FFFF) << 8) | (slot as u32)
```

`debug_assert!` 在**正式发布版里被编译掉**，`& 0x00FF_FFFF` 会把超限页号**悄悄绕回**。

**后果**：属性指针指向错误页 → **读到别的实体的数据，且不报错**。

**触发条件**：文件超过 64 GiB。你写小说到不了，但这是数据库最坏的失败模式，必须堵上。

### 事实三：那个"快写完了"的说法不成立

实测 O(N²) 查询**完全没动**：

```
边数      1000      2000      8000      32000
耗时     117ms     393ms   10,639ms   158,096ms   ← 2.6 分钟
```

`LIMIT 1` 也救不了（32k 边仍需 62 秒）——它先全部展开，最后才截断。

## 第 2 节：成熟产品的共同路径（研究结论）

我把它们的演进提炼成四个阶段。**关键洞察：所有成熟数据库都在"格式冻结"这一步之后才开始被信任。**

```
阶段一：能跑（MVP）
  └─ 存数据、查数据、别崩
     ✓ 已完成

阶段二：不丢数据（可信赖）
  └─ ACID、崩溃恢复、坏页检测、格式冻结承诺
     ✓ 已完成 90%，差「格式冻结承诺」这最后一步

阶段三：能用（可日常）
  └─ 查询够快、多端并发、能备份
     ✗ 当前卡在这里 ← 本轮重点

阶段四：好生态（被采用）
  └─ 多语言 SDK、官方包、可视化、文档
     ✗ 未开始
```

**两个反面教材必须记住**：

- **Kuzu**：技术很强（CSR 邻接、向量化执行），但 2025-10 仓库突然归档被 Apple 收购，用户被迫迁移。**教训**：格式不冻结 + 治理不透明 = 用户不敢用。
- **CozoDB**：功能很全（Datalog、时序、向量），但作者精力分散，2024 年后基本停滞。**教训**：一次做太多不如做透核心。

**我们的策略**：不追求功能最多，追求**核心做透 + 格式冻结 + 长期承诺**。这正是 SQLite 的路线。

## 第 3 节：七批工作（一个都不删）

按依赖顺序。P0-P2 是"能用"的门槛，P3-P4 是"敢用"，P5-P6 是"好用"。

### P0 — 去 bincode + 边界硬化 + 格式冻结承诺

**为什么必须现在做**：`bincode` **已经停止维护**。它的 3.0.0（2025-12-16）内容只有一句
墓志铭——作者遭遇人肉骚扰后终止项目，那个"版本"里只有一个编译错误和一段说明，
目的是让用户知道这库死了。

而它**焊死在磁盘格式里**：

```rust
// src/storage.rs:121 —— WAL 每一帧的编码
let payload = bincode::serialize(record)?;
// src/disk_graph.rs:1116 —— Page 0 的字典与索引目录
let dict_bytes = bincode::serialize(&self.dict)?;
let cat_bytes = bincode::serialize(&self.index_catalog)?;
```

我们锁的是 `bincode 1.3.3`（2021 年）。它能跑，但**永远不会再有安全修复**。
若在此时冻结格式，就是把数据库的寿命钉死在一个已弃坑的依赖上——
**这正是 Kuzu 的教训重演**。

**你的库还没有数据，这是改格式唯一的免费窗口。** 现在改零迁移成本；
冻结之后再改就是破坏承诺。

**四项工作**：

1. **手写 WAL 与元数据编解码**，替换 `bincode`（约 240 行）
   - `WalRecord` 五种变体：定长前缀 + 长度前缀的 payload
   - `StringDict` / `IndexCatalog`：变长字符串集合
   - 格式必须**显式文档化**，不能再依赖第三方 crate 的字节布局
2. **`pack_prop_ptr` 改为运行期检查**，超限返回明确错误（不再静默截断）
3. **打开时检查文件大小**，超过 64 GiB 拒绝启动并说明原因
4. **新增 `FORMAT.md`**：磁盘布局、各项上限、**冻结承诺**、未来变更流程

**冻结承诺的措辞**（参照 SQLite 原文）：

> 自 1.0.0 起，GraphLite 的磁盘格式不再以不兼容方式变更。未来版本永远能读写
> 1.0.0 创建的文件。若某项特性必须改变格式，将采用 DuckDB 式的
> `STORAGE_VERSION` 显式选择，旧格式继续受支持。

**这是一次破坏性格式变更（v3 → v4）**，已获授权。变更后格式冻结。

---

### P1 — 查询引擎：起点锚定 + LIMIT 短路

**为什么最痛**：158 秒和 1 毫秒的区别，决定你敢不敢在界面上随便点。

**问题**：`MATCH (a)-[r]->(b) WHERE id(a) = 5` 会**先展开全库所有边**，再过滤。

**做法**：

1. 从 `WHERE` 提取能钉住节点的条件（`id(a)=5`、`a:Character {name:"林渊"}`）
2. 从被钉住的节点出发，**沿它的邻接链走**，而不是扫全库
3. `LIMIT n` 凑够 n 行就停
4. `EXPLAIN` 让人看到实际用了哪条路径

**预期**：32k 边场景 158,000ms → **毫秒级**。

**风险控制**：用已有 `differential_test.rs` 做差分对照，改前改后结果必须逐位一致。

---

### P2 — 多读并发：1 写 + N 读

**为什么**：你的场景是"Agent 后台写，你前台看"。现在做不到——同时只能开一个句柄。

**做法**（参照 SQLite WAL 模式）：读者拿共享锁，写者拿排他锁。

**难点**：只读打开时若 WAL 有待回放内容，就变成写了。必须在**打开阶段**判定清楚。

---

### P3 — 唯一约束

**为什么**：这是"数据不脏"的保证。没有它，Agent 可能给同一个角色建两个节点，而你不知道。

对标：所有成熟数据库都有。

```cypher
CREATE CONSTRAINT ON (c:Character) ASSERT c.name IS UNIQUE
```

写入重复值时报错。这是**防止 Agent 写坏数据的最后一道防线**。

---

### P4 — 运维：`vacuum` + `backup`

- `vacuum()`：回收已删记录占用的页（删章节后能真正释放空间）
- `backup(path)`：在线热备出一致副本（现在只能 `.dump` 出文本）

---

### P5 — SDK 性能（你明确提到的问题）

**根因**（已定位）：SDK 每写一条都要**跨一次语言边界** + 拿一次全局锁。

**做法**：批量接口。一次跨边界提交一批。

```python
# 现在：10 万次跨边界 → 63k ops/s
for n in nodes: tx.add_node(n)

# 之后：1 次跨边界 → 预期 300k+ ops/s
tx.add_nodes(nodes)
tx.add_edges(edges)
```

**预期**：把 9 倍差距（63k vs 550k）压缩到 2 倍以内。

### P6 — 工具：`graphlite studio`（可视化）

**你的判断对**：图数据用字符终端看是逆天而行。关系型输出二维表格很适合终端，图是网状的，看不出来。

**方案**：`graphlite studio novel.db` → 自动开浏览器。

- 力导向图看人物关系网，可拖拽缩放
- 点节点看属性
- 按类型/章节过滤
- 勾选"未填伏笔"高亮所有未回收线索
- 网页里写 Cypher，结果直接画成图

**关键约束**：Studio 是**独立二进制**，不塞进核心库。核心库保持零依赖、单文件、轻量。

**CLI 不动**（按你的要求）。

---

### P7 — 减依赖（放最后）

**先解释为什么**：依赖就是"引用的别人写的代码"。风险有四个：

1. 作者弃坑（Kuzu 就是活例子）
2. 升级后破坏你的项目
3. 安全漏洞
4. 编译变慢

SQLite 坚持零依赖，这是它能用 20 年的原因之一。

**当前 5 个依赖的实际可减性**：

| 依赖         | 用途           | 能不能去掉                     | 工作量 |
| ------------ | -------------- | ------------------------------ | ------ |
| `crc32fast`  | CRC32 计算     | ✅ 能，手写查表实现约 60 行    | 小     |
| `thiserror`  | 错误类型样板   | ✅ 能，手写 `Display` 约 80 行 | 小     |
| `bincode`    | 索引目录序列化 | ⚠️ 能，但要自己写编解码        | 中     |
| `serde_json` | C API 的 JSON  | ⚠️ 能，但要手写 JSON 解析      | 中     |
| `serde`      | 派生宏         | ❌ **不建议**，牵涉最广        | 大     |

**建议**：先做 `crc32fast` + `thiserror`（低风险、收益明确），`serde` 留着。目标是 **5 个减到 3 个**，不是追求零依赖而把代码搞复杂。

## 第 4 节：明确不做的

| 项目                           | 理由                                               |
| ------------------------------ | -------------------------------------------------- |
| 百核并发压测                   | SQLite 都不做。单机场景无意义                      |
| 代价模型优化器（CBO）          | 为多表 join 排序设计。图遍历用规则优化器（P1）就够 |
| 分布式/多集群                  | 设计前提是单文件嵌入，与 SQLite 一致               |
| 内存图模式                     | 违反有界内存这一核心架构前提                       |
| 全文/向量索引                  | 另一个问题域                                       |
| `MERGE`/`UNWIND`/`WITH`/子查询 | 需要设计而非打补丁                                 |

**"节点事务分块"降级**：P1 修好后危害大减，保留在低优先级。

## 第 5 节：开发规范更新（防误删）

我会犯过的那次错——**未跟踪文件被 `rm` 后无法恢复**——写进 `AGENTS.md`：

1. **禁止 `rm` 删除未跟踪文件。** 移到 `./.trash/<时间戳>/`，确认后再手工清理
2. **可能影响未跟踪文件的操作前，先 `git add`** 纳入版本控制
3. **不用 `git stash` 隔离验证**（未跟踪文件不进 stash）。改用 `git worktree`
4. **分批提交**：每批独立可编译可测试，用 `git add <具体路径>` 而非 `git add -A`

## 第 6 节：验证方式

每批必须过 CI 门禁：

```bash
cargo fmt --all -- --check
cargo check --workspace --all-targets
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps
```

外加真实数据基准与红线：

- LiveJournal 边写入 ≥150,000 ops/s
- Hub 1-hop / 2-hop **逐位一致**（335,194 / 10,027,730）
- 最小库 ≤16 KB

**性能声明必须带测量条件**（既有规范）。

## 第 8 节：交付节奏

严格按 P0 → P7 顺序，每批：

1. 独立分支
2. 独立提交（可编译、可测试）
3. CI 全绿
4. PR 合并后再开下一批

**P0 与 P1 的硬依赖**：冻结格式前必须确认 P1 不改存储（已确认，P1 只改查询执行）。

**版本策略**（按你的决定）：

- P0-P7 全部完成后发 **`1.0.0-rc.3`**
- 你实际使用一段时间（写小说、跑 Agent）
- 确认无问题后再发 **`1.0.0`** 正式版
